# 智能体工作流说明

> 项目：AI 原生 Enterprise Architect（Web 版）｜仓库：EA_fake
> 周期：2026-08-24 起，**9 个开发日、跨 42 天**，120 次提交
> 本文说明**如何用智能体开发这个项目**，以及**凭什么相信智能体做对了**。

---

## 0. 一句话

这个项目的开发方式不是「让智能体写代码」，而是三件事：

1. **给智能体建基础设施** —— 自建跨会话记忆系统，让每次会话的结论不丢失；
2. **给智能体定验收标准** —— 用真实编译器、真实数据库、真实框架、真实浏览器校验它的产出，而不是相信它的自我报告；
3. **把每次失败沉淀成机制** —— 每个踩过的坑都变成一条规则、一个断言或一项检查，防止复发。

代码由智能体生成。**下面全部内容是关于"怎么指挥"和"怎么验收"的。**

**spec 与 plan 成对、按日期命名，且能对应到实现提交：**

**plan 不是散文，是「可执行任务书」**：每个 task 带 `**Files:**`、`**Interfaces:**`、`- [ ] Step N`、

（逐条核对 spec 覆盖、占位符、类型一致性）。

**验证被写进 plan 的每一环**，例如：

```
Run: cd EA_fake/ea-webapp && ./node_modules/.bin/vue-tsc --noEmit
Expected: PASS（无类型错误）
```

### 1.3 模型路由策略

常规编码默认用低成本快速模型，**仅在确实卡住时才升级到推理模型**。
依据是「多数实现工作是机械的，不需要昂贵模型」——主动的成本控制，而非默认行为。
SDD 流程中确实按难度分层：任务级评审用常规模型，**最终全分支评审升级到高能力模型**。

### 1.4 版本控制与日志

- GitHub 私有仓库，**按工作日提交**（有开发才提交，跨 42 天共 9 个开发日），用于单日出问题时的回退
- 每日开发日志：`docs/dev-logs/YYYY-MM-DD.md`，结构为「今日主题 / 完成事项 / Bug 修复 / 遗留待办 / 验证情况」，随代码一起提交

**这套记录补上了 git 记不住的部分**：git 记录"改了什么"，日志记录"为什么这么改、验证到什么程度、什么没做完"。

## 2. 自建记忆系统

智能体默认**不记得上一次会话**。为解决问题，项目自建了一套跨会话记忆：

```
会话结束
  → SessionEnd hook 触发（.claude/hooks/session_summary.py）
  → 解析本次会话记录
  → 调用模型生成中文总结
  → 写入 memory/session-logs/YYYY-MM-DD_HHMMSS_<会话id>.md
  → 在 MEMORY.md 幂等追加索引行
```

| 设计点 | 取值 | 理由 |
|---|---|---|
| 有效会话阈值 | 用户文本 ≥ 2 条才写 | 避免给单句问候生成无意义总结 |
| 失败行为 | 任何异常静默 `exit 0` | 绝不阻塞会话关闭 |
| 摘要保留策略 | 开头 4 条 + 结尾 60 条 | 保留初始目标与最近工作 |
| 喂给模型的上限 | 30000 字符 | 控制成本 |

**产出**：20 篇自动生成的会话日志，每篇含「主题 / 做了什么 / 决定结论 / 遗留待办」四段。
这些日志**诚实记录了失败**——例如「两次上下文超限报错」「多处改动未提交」。

另有 12 条人工维护的结构化记忆，每条含 **Why** 与 **How to apply**。

> ⚠️ **材料提交提示**：`.gitignore` 排除了 `.claude/`，且记忆与 plan 存放在用户目录下
> （`~/.claude/projects/<项目>/memory/`、`~/.claude/plans/`）。
> **若要作为参赛材料提交，这部分必须单独打包**，否则工作流证据会缺一半。

## 3. 验收机制：不信任智能体的自我报告

### 3.1 三层真验证（针对「图 → 若依模块」产物）

| 层 | 手段 | 结果 |
|---|---|---|
| 后端编译 | Maven + 官方 RuoYi-Vue 3.9.2 真实工程 | BUILD SUCCESS，**全项目 0 错误 0 警告** |
| 前端编译 | `@vue/compiler-sfc` + TypeScript | 6 个文件全过 |
| SQL 真执行 | MySQL 8.0.29 | 零 ERROR，4 张表（含复合主键中间表）+ 菜单 |

**为什么要建**：此前**从未真编译过**——本机无 JDK/Maven/MySQL，所有验证都是静态的
（查 import 完备性、括号配平、XML 解析）。而 `pom.xml` 的 `<parent>` 坐标必须与目标工程一致，
**不能猜**。于是专门搭了本机便携验证环境（不写注册表），把静态验证升级成真编译。

**关键点：不执行第三方仓库的代码。** 前端检查器使用本项目已装的工具链，
不克隆外部仓库跑 `npm install`（那会执行对方自己的生命周期脚本）。这是刻意的安全约束。

### 3.2 验证器本身也要被验证

两个检查器都做了**反向验证**：喂入故意写坏的文件，确认检查器会报错。
**这一步是为了排除"恒过的安慰剂检查器"**——一个永远返回成功的检查器比没有检查器更危险。

检查器内嵌自证注释：「已验证检查器本身有效：故意写坏的 `.vue` 能报出「插值未闭合/标签未闭合」，
故意写坏的 `.ts` 能报出「':' expected」等语法错误——不是恒过的安慰剂。」

同一原则贯穿：新增 20 条防漂移断言后，**又验证断言本身有效**（喂残缺枚举确认会报出缺失项）。

实测有效：改前端产物时检查器抓到 `el-col` 配平错误。

### 3.3 检查器从测试搬到生产侧

原来自检器只活在测试文件里，测试实际是**「测自己的副本」**——生产代码改了它不会红。
搬到 `backend/code_lint.py` 后，测试改为 import 本模块，**变成对生产实现的回归锁**。

自检器「只收集、永不抛异常」——产物问题不该让整个生成失败；但**自检器自己出错也要如实报出，不能静默当成「没问题」**（此行为有专门断言）。

### 3.4 离线可复现测试

四套离线测试，共 **526 条断言，全绿**：

| 测试 | 断言数 | 覆盖 |
|---|---|---|
| `test_ruoyi_gen.py` | 110 | 若依产物生成 |
| `test_ruoyi_api.py` | 51 | 若依接口 |
| `test_ai_quality.py` | 128 | AI 质量保障链 |
| `test_golden_regression.py` | 237 | 黄金样例回归 |

**黄金回归的设计思想**（其 docstring 原文）：

> **为什么离线模式能抓到东西**：它不测「模型说了什么」，只测「拿到这样一份产出之后，
> 后端的加工链路是否自洽」—— id 是否连续、关系端点是否都解析得到、类型是否越界、
> 布局是否重叠、打分器是否真的在排序。这些正是 prompt 改坏时最先崩的地方，而且完全可复现。

LLM 调用被替换为**会抛异常的桩**，并断言「全程 0 次 LLM 调用」。
离线必须强制关 AI 的根因也被查明：配置层在 **import 时**就读取数据库中的 AI 配置，
开发机存过 key 时"离线"测试会真的联网并随机失败。

### 3.5 AI 输出质量保障（`ai_quality.py`，729 行纯函数）

1. **校验-回喂修复循环** —— 生成后自动校验，把问题回喂给模型修复（**刻意只跑一轮**以控制成本）
2. **Best-of-N 采样择优** —— 默认采样 3 次，用确定性打分器选出最优，**只对赢家做修复**（修复要花调用，不该修输家）
3. **确定性打分器** —— **永不接受 model 参数**，只接受 issue 列表 + 结构统计量，保证可复现
4. **产物结构自检**
5. **跨图命名对齐**
6. **诚实计数** —— `applied_ops` 记录**真实生效的操作数**，而非模型声称的数量

### 3.6 真实浏览器自动化验证

用 **Edge headless + CDP** 做真机验证（Node 自带 WebSocket，**不需要 puppeteer/playwright**，
几十行脚本即可）。**为什么必须做**：`vite build` 抓不到运行时报错——
**曾经因此漏掉一个 `computed is not defined` 的整页白屏**。

实测覆盖：登录 → 画布拖动平移 → 模拟触屏双指缩放 → 三击删除 → 双击编辑。

### 3.7 路由数守恒

拆巨石重构全程立了一条回归标准：**每步 `py_compile` → 导入后验证路由数 258 → 重启 → 端到端冒烟**，
四项都过才提交。

## 4. 纠偏案例集

> 本文核心。每个案例记录：智能体错在哪 → 怎么发现的 → 怎么修的 → **沉淀成了什么机制**。

### 4.1 依赖版本靠猜，三项全错

- **现象**：生成若依模块 `pom.xml` 时按假设的版本号写 `<parent>` 坐标
- **发现**：实拉官方工程核对，假设的 **3.9.0 / Spring Boot 3 全部错误**，实际 **3.9.2 / Spring Boot 4.1.0 / Java 17**
- **修复**：改为实拉核对；版本做成可配置项（默认 3.9.2，带格式校验）
- **沉淀**：确立「**先拿事实，不猜**」原则，并把它写成 plan 的**第 0 步**
  （plan 原文：「没有这步，pom 模板就是猜的」）；事实写进模板注释作为依据

### 4.2 复合主键静默降级，代码与 DDL 不一致

- **现象**：多主键表只把第一个主键当主键，其余降级为普通列，**但 DDL 仍按复合主键写全**
- **影响**：中间表这类"必中"的表，生成的 CRUD 是错的，只在文档留一句「需手工调整」
- **修复**：改为联合主键完整实现（多参数 + `@Param` + 两段路径 + 不生成批量删除 + 不加自增）
- **沉淀**：**加回归断言锁住单主键产物逐字未变**——修 A 不能碰坏 B

> 顺带发现一个编译期看不出的坑：多参数方法不加 `@Param` 时 MyBatis 只认 `param1/param2`；
> 想用命名参数必须**同时**满足「编译带 `-parameters`」和「`useActualParamName=true`」，
> 任一不成立就在**运行时**报错。已逐个加注解堵死。
>
> 另注：若依官方假定单主键，**联合主键没有官方范式**，这套是自定义的自洽方案——
> 已在 README 写明，避免用户误以为与官方一致。

### 4.3 一个「我以为的 bug」被真实数据库否掉

- **现象**：DDL 里有 `auto_increment=1`，而该表没有自增列 —— 判定为 bug，准备修改
- **发现**：真实 MySQL 跑下来**不报错，直接忽略**
- **结论**：不改
- **沉淀**：「**验证的价值不只是证明对，也包括证明"你担心的不是问题"**——幸好是跑了而不是照着怀疑改」

### 4.4 提交信息里的内容被静默吃掉

- **现象**：`git commit -m "…带反引号的中文…"`，bash 把反引号当命令替换，提交信息里那一段**静默消失**——不报错、不留痕
- **发现**：stderr 冒出 `a/b/c: No such file or directory`、`{}: command not found`
  —— **不是命令却报 command not found，就是它在作祟**
- **修复**：`git commit --amend -F 文件`
- **沉淀**：写成记忆规则，含**诊断特征**与操作步骤；判据是「中文技术提交信息里几乎必然写反引号包代码，所以这不是偶发」

### 4.5 SDD 评审抓到缩放比写反

- **现象**：`ctx.setTransform` 缩放比写反（`dpr*sx` 应为 `dpr/sx`）
- **发现**：**子代理评审**（任务级评审流程）抓到
- **沉淀**：修复代码的同时，**同步修正 spec 与 plan 里的错误写法**——
  「评审产物本身也要回修」，不留错误文档

### 4.6 页面过渡破坏画布初始化 → 回滚后换路线重做

- **现象**：`<Transition mode="out-in">` 包裹 tab 内容改变了 DOM 插入时机，与画布 `nextTick` 初始化冲突 → **画布彻底不可用**
- **发现**：上线后**用户反馈**
- **修复**：立即**回滚**到已知良好版本并重新部署（保留 `dist.bak.*` 备份）
- **再实现**：换路线——**纯 CSS 动画，不改 DOM 结构**，画布初始化不受影响
- **沉淀**：形成「回滚优先于现场修」的处置习惯

### 4.7 「数学验证通过」≠ 真机通过

- **现象**：画布"拖不动"。前一轮只改了 view 数值（**数学验证通过**），但 `viewPanning` 分支**漏了重新应用 canvas 变换** → 画面不跟随
- **发现**：真机实测
- **沉淀**：确立「前端改动必须走真机验证」——后续引入 Edge headless 自动化

### 4.8 无限画布触屏四 bug（同一根因族：逻辑坐标 vs 屏幕坐标）

| 现象 | 根因 | 修法 |
|---|---|---|
| pinch 双指缩放乱跳 | 用逻辑坐标跟踪触点，视图缩放后坐标随之变化 | 触点改用**屏幕坐标** |
| 画布拖不动 | 平移用逻辑坐标差值，**累积漂移** | 平移用屏幕位移 / scale |
| 三击删除生成新类且删不掉 | 依赖浏览器 `dblclick`，触屏常不触发 | 纯 click 计数（时间窗 + 屏幕位置 + 命中同一元素） |
| 缩放后放置元素不可见 | 坐标换算 | 同上族 |

**沉淀**：一条根因族被识别出来，后续改动统一按「屏幕坐标 / 逻辑坐标」边界检查。

### 4.9 离线测试偷偷联网，随机失败

- **根因**：配置层在 **import 时**就读数据库里的 AI 配置；开发机存过 key，`enabled` 为真
- **修复**：强制 `enabled = False` + 调用替换为抛异常的桩 + `finally` 还原
- **沉淀**：写入记忆「三个坑，别再踩」；同一坑在 spec、记忆、测试 docstring **三处记录**

### 4.10 校验器不是纯校验器

- **现象**：`validate_uml_model` / `review_archimate_model` **内部会调用 LLM 做语义评审**
- **影响**：任何「打分 / 离线测试 / 可复现比较」路径若不加处理，会**静默发请求且结果不可复现**
- **修复**：此类路径必须传 `use_ai=False`
- **沉淀**：写入记忆；打分器设计上**永不接受 model 参数**以在结构上杜绝

### 4.11 浅拷贝别名缺陷，摧毁诚实计数语义

- **现象**：`_apply_er_edits` 用浅拷贝 `[dict(e) for e in erEntities]`，`add_field` 的
  `target['fields'].append(...)` 会**原地改掉调用方的模型**（实测：调用方 fields 从 1 变 2）
- **影响**：让「报告说 0 步生效、模型其实已被改」成为可能，**直接摧毁诚实计数的语义**
- **修复**：深拷贝
- **沉淀**：作为质量保障设计的「先决发现」写入 spec

### 4.12 白名单散在三处，各自漂移

- **现象**：ArchiMate 的元素/关系/层次白名单散在三处——① 校验代码 **13 处** in/not in
  ② 提示词枚举串 **6 处**硬编码 ③ 前端调色板
- **影响**：改一处忘一处就会出现「**提示词让模型输出 X，后端白名单只认 Y**」——
  模型照提示词给出的类型被后端静默改写，**非常难查**
- **修复**：收敛到 `constants.py` 单一来源，提示词枚举改为派生
- **细节决策**：用**有序元组而非 set**——提示词要把它们拼成斜杠分隔的枚举串给模型看，
  顺序必须稳定，不能靠 set 的迭代顺序（每次启动可能不同）
- **沉淀**：**先存提示词基线、改完逐字节比对**（三个提示词 728 / 544 / 1264 字符一字不差）
  + 20 条防漂移断言，并验证断言本身有效

### 4.13 装饰器被挂到辅助函数上

- **现象**：插入 `_edit_counts` 时，`@app.route` 落到了路由装饰器与视图函数之间，
  Flask 把 URL 路由到了辅助函数上
- **发现**：**由接口契约测试抓到**
- **沉淀**：接口契约测试成为常规手段

### 4.14 空画布提示被当成可修问题

- **现象**：把「画布为空」也报成 warning，导致只有 ER 的健康模型被判成「有问题」，**白花一次 LLM 调用**
- **修复**：修复循环与打分器都滤掉 `type=='empty'`（顺带消掉与覆盖度惩罚的重复扣分）

### 4.15 跨图命名报告噪音

- **现象**：`ArchiMate「OrderService」与 UML 类「Order」`——角色后缀是三图之间的惯用对应，
  **报出来会淹没真正该看的问题**
- **修复**：加抑制规则
- **沉淀**：安全阀——「中文名与英文名绝不互改；key 过短/纯数字不判定；同一名字匹配到多个候选 → 降级为只报告」

### 4.16 构建不报错但页面白屏

- **现象**：`userInfo` 用了 `computed` 但没导入 → 整个 AI 页白屏。
  **`vite build` 不报错**（不做未定义变量检查），浏览器里跑起来才抓到
- **沉淀**：写入本机验证环境记忆，前端改动必须走真机验证（后引入 Edge headless 自动化）

### 4.17 重复路由注册（已识别，**未修复**）

- **现象**：`app.py` 中 **19 个 URL 路径被重复注册**（其中 2 个注册了 3 次，合计约 21 处多余注册）。
  Flask 只让**先注册者**生效，后注册的实现成为**不可达的死代码**
  （已具名：`/api/v1/project/create` 973 与 2328、`/api/v1/project/list` 1009 与 2391、
  `/api/project/<id>/config` 1091 与 2644 等）
- **影响**：若后注册的是修复版本，则**该修复从未生效**
- **状态**：**已识别，未修复** —— 列入已知不足
- **附带发现**：项目早期的一次审计把生效顺序**记反了**（写成"后注册者生效"）。
  经**实测**确认 Flask 用的是先注册者。**连审计结论也要实测**——这条已作为教训记录

## 5. 设计决策：主动把不确定性挡在关键路径外

### 5.1 若依代码骨架刻意不调用 LLM

生成的若依模块，**代码骨架完全由确定性逻辑生成，不经过模型**：

- 无 `max_tokens` 截断风险，**AI 服务挂掉也能产出完整可用模块**
- 模型只用于补充中文注释，且**每个字段都有确定性兜底**

体现「理解模型失效模式」：把不确定性限制在装饰性内容上，核心产物走确定性路径。

### 5.2 诚实计数而非采信模型自述

`applied_ops` 统计**真实生效的操作数**，不是模型声称的数量。模型的自我报告不作为事实来源。

### 5.3 不擅自改用户数据

跨图命名对齐的产品决策：「高置信自动改，其余只报告」——**不擅自改用户数据**，同时消掉确定性的机器噪音。
部分场景（如 `Order` ↔ `orders`）**既不自动改也不报告**，因为强行统一会污染若依产物与 DDL 表名。

### 5.4 已知边界主动记录

系统**做不到**什么被明确写下：

- 修复循环按**名字**寻址，所以「未命名元素」「悬空关系」这类错误**修不了**——坏掉的东西没有合法名字
- ER 在降级路径**无确定性兜底**（单图路由有，智能体降级路径没有），已写进黄金测试的 `[已知缺口]`
- `finish_reason` 截断信号**只迁移了 2 条路径**，其余约 8 个 LLM 辅助函数仍可能把半截 JSON 当作成功
